# P25 Phase 1 on the Retevis C62

Status as of 2026-11-04: **P25 Phase 1 transmit and receive work on the C62.**
A real P25 subscriber radio decodes the voice, and `dsd-fme` decodes the same
transmission with zero IMBE/LCW errors.

Everything here lives on the N4IRS fork only:
`github.com/N4IRS/OpenRTX`, branch **`c62-m17-plus`**.

## 1. Operation

All P25 settings are **global**, not per channel: there is no `p25Info_t` in
`channel_t` yet (see `docs/chirp-cps-feasibility.md`).

P25 Settings menu:

| Item | Value used here | Notes |
|---|---|---|
| `DMR Id` (source) | `3112138` | Unit ID sent in the LCW |
| `Dst Id` | `3166` | Talkgroup |
| `NAC (hex)` | `0x125` | Entered and shown in hex (0x125 = 293 decimal, as dsd-fme prints it) |
| `RX Level` | `100` | Baseband input gain; `P25_IO` resets it to 100 if stored as 0 |
| `TX Level` | `160` | Baseband output amplitude; `P25_IO` resets it to 160 if stored as 0 |
| `RX Invert` | `ON` | **Required on the C62 to lock** |
| `TX Invert` | `ON` | Compensates the BK4819 mic-path audio → deviation inversion |

### Editing RX / TX Level

`ENTER` on the item opens a number-entry screen showing the current value.

- type the value with the keypad (3 digits, 1…255)
- or step it with `UP` / `DOWN` (±1)
- `ENTER` saves, `ESC` cancels

The value is written to `settings.p25_tx_level` / `p25_rx_level` and persisted
in the CRC-protected settings record by `nvmem_C62.c`.

`TX Level` is a plain baseband scale factor: `P25TX.cpp` multiplies the IMBE
output by `m_txLevel * 128` in Q15, so 160 ≈ 0.625 of full scale. 160 is the
value verified on air; much higher values can clip the deviation.

### TX polarity

P25 symbol levels in `P25TX.cpp` follow TIA-102.BAAA:

```
P25_LEVELA = -1260   P25_LEVELB = -420   P25_LEVELC = +420   P25_LEVELD = +1260
```

`dsd-fme` must report `+P25p1`. A `-P25p1` lock means the levels are inverted.

## 2. Verifying a transmission

Live decode with the RTL-SDR (the radio transmits on 446.900 MHz, NAC 293):

```bash
export LD_LIBRARY_PATH=/tmp/mbelib:/srv/Backup/NUC/rtl-sdr/build/src
/srv/WorkSpace/reference-code/dsd-fme/build/dsd-fme \
  -i rtl:0:446.9M:40:0:12:0:2 -o null -Z -c /tmp/dibits.bin
```

`-o null` is required (no audio device on the test host). Gain 40 is enough
for a live decode; 29.7 dB was starved. Decode is insensitive to gain between
20 and 49.6 dB once the baseband is correct.

A good key-up looks like:

```
Sync: +P25p1  NAC/CC: 293;  HDU
HDU  ALG ID: 0x80 KEY ID: 0x0000 MI: 0x0000000000000000
Sync: +P25p1  NAC/CC: 293;  LDU1
IMBE 040CFD7BFB7DF27B3D9E45 err = [0] [0]
LCW Circuit Priority 0 Group Voice Channel User - Group 3166 Source 3112138
```

Checklist:

- every sync is `+P25p1`;
- the **first** sync of a key-up is followed 432 symbols later by the second
  one (that frame is the 216-byte HDU followed by one 9-byte half-buffer of
  padding), then all spacings are **864 symbols / 216 bytes**;
- HDU decodes at the start of the transmission;
- LCW FEC errors are 0, IMBE words mostly `err = [0] [0]`;
- no `duid:EE` (that is dsd-fme's NID BCH failure, `dsd_frame.c:408-413`).

Offline analysis from a raw IQ capture: `rtl_sdr -f 447150000 -s 2400000
-g 40.2 -n <samples> out.iq8`, then `iq2wav.py` draws an audio WAV for
`dsd-fme -i file.wav`.

## 3. What was broken

### 3.1 Symbol polarity

The P25 TX symbol levels were the exact inverse of TIA-102.BAAA, so
`dsd-fme` locked `-P25p1` and a real radio did not unmute. Levels are now
negated (`-1260/-420/+420/+1260`), verified on air.

### 3.2 Codec replaying baseband halves

Symptom: frame syncs every **1152** symbols instead of 864, a second sync
72 symbols (18 bytes) into each frame, dsd-fme finally giving up with
`duid:EE`.

Root cause: the producer generated a complete frame (4320 samples) before
handing anything to the codec. The CSK6 audio worker (`csk6_codec.c`,
`output_sample()`) wrapped the TX double buffer and replayed a half whenever
the producer missed a boundary. Each replay duplicated 72 symbols, stretching
every frame by 4/3.

Fix:

- `P25TX.cpp` drains the codec per byte (`update_tx(20, false)`);
- `P25_IO::update_tx()` gained a `flush` flag so the final partial half is
  pushed instead of waiting for a boundary;
- the TX half-buffer was grown from 180 to 720 samples
  (`P25_TX_HALF_SAMPLES`).

Evidence: the only exact repetition lag in the C62 dibit stream was 72
symbols (≈20 % of all symbols); the offline harness with a stubbed
`update_tx()` showed none.

### 3.3 The HDU was not broken

An `duid:EE` frame at key-up was initially blamed on the HDU builder. It was
the same framing bug: no capture before the fix had ever included the start of
a transmission. Once captured, the radio's HDU is byte-identical to the
known-good offline harness HDU (NID `29 30 0E CE D7 7E 00 70`); only the final
padding byte differs (`00` vs `02`). It decodes as
`HDU ALG ID: 0x80` right before the first LDU1.

Note that an HDU is optional for unencrypted P25 group calls — the reference
radio unmutes even without it — but it is now sent correctly.

### 3.4 Baseband level menu

The P25 RX/TX level entries opened an edit screen that never initialised the
input buffer, ignored keypad digits, displayed no value and ignored `ESC`.
The only working gesture was DOWN-then-ENTER (decrement by 1, blindly).
`ui.c` now drives the same numeric-entry path as the ID fields: current value
visible, digits accepted, `UP`/`DOWN` stepping, `ENTER` commits (clamped
1…255), `ESC` cancels.

The `NAC` entry was labelled `NAC (dec)` although it is parsed with base 16
and displayed as `0x%03X`; the label now reads `NAC (hex)` to match.

## 4. Known limitations

- P25 **Phase 1** only: no Phase 2, no trunking, no encryption (ALG ID 0x80 =
  unencrypted is hard-coded in the HDU/LDU).
- P25 configuration is global, not per channel (see the CPS notes).
- `TX Level` is an amplitude, not a calibrated deviation control; use 160
  unless a deviation meter says otherwise.
- The receive path needs `RX Invert = ON` on this board because of the BK4819
  discriminator polarity.
